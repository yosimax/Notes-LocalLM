Local LLM 性能分析レポート case2

llama.cpp の llama-server ログを解析し、スロット context サイズ と prompt (prefill) 速度・generation 速度 の関係を定量化した。本番は case2 の mactop リポジトリ調査タスク（3 種モデル）を主軸に、case1（2026-09-11 の Qwen 実行）を参照とする。

生成日: 2026-09-18  |  ソース: case1/*.log case2/*.log  |  解析スクリプト: analyze.py

1. 要約（エグゼクティブサマリー）

  • context が大きくなるほど prefill・generation の両方が遅くなる。 全モデルで、スロット context が ~10K→60–70K に伸びる間に generation 速度が落ち、prefill 速度も同様に低下（attention 計算量が KV キャッシュ量に比例するため）。
  • モデル差が最大。 9B 級（Q4_K_M / Q8_0）は ~11–15 / ~8–11 t/s、27B 級（Qwen Q2_K_XL）は ~4–6.5 t/s。9B が 27B の 約 2–3 倍速い。
  • 量子化差は小さいが実在。 同 9B 同士で Q8_0 が Q4_K_M より ~1.3–1.5 倍遅い（重み大）。
  • コンテキストリセットで速度が回復する。 context が ~62–65K 附近で slot がリセットされる（opencode auto-compaction / 新セッション）。リセット後は低 context 相当の速度に戻る（例: Qwen 3.83 → 4.82 t/s）。
  • 128K スロットは session 中にリセットされず（compaction 閾値に届かず）。ctx 60–70K でも 11–12 t/s を維持（ただし高 ctx 域では同様に低下）。

6. 解析メソドロジー

  • task の定義: launch_slot_（= リクエスト開始）から release ... stop processing（= 終了）までを 1 タスク。
  • ctx: 終了時 stop processing: n_tokens。スロット KV キャッシュ総量（＝その時点の conversation+生成 相当）。
  • prefill 速度: 最終 prompt eval time = X ms / N tokens を N/(X/1000) で t/s に換算（= そのリクエストの prefill 平均）。
  • generation 速度: 最終 eval time（= N tokens / ms）と n_gen 行の tg（トークン毎速度）を併記。tg は 100 tok 以上生成したタスクのみ取得。
  • prefill 進捗: prompt processing, progress=… 行の t/s から、KV 増大に伴う prefill 内の速度低下を可視化（例: Qwen task 2611 は 52.8→41.6 t/s）。
  • 時刻: M.SS.mmm.uuu を秒数に換算（分*60+秒+ms/1e3+us/1e6）。
  • 中断タスク: cancel task（ユーザー中断）は pre/gen が 0 になるため速度集計から除外。
  • LCP 再利用: f_sim_best / f_keep で slot が再利用される。prefill の prompt eval トークンは「差分」のみを処理するため、再利用リクエストは prompt tok が少なく高速に見える点に注意。

7. 注意・限界

  • prefill 速度は「リクエストごとの prompt 差分」に対して算出。slot 再利用（LCP）が多いセッションは差分が小さく数値が跳ねる。傾向（ctx↑⇒速度↓）を見る用途には妥当。
  • tg（generation 速度）はタスク内 100 tok 毎に 1 行のみ。低 ctx タスクで生成 100 tok 未満のものは tg が無い（gen t/s は eval time から取得）。
  • compaction の発火閾値は opencode 設定 keep.tokens=15000 / buffer=20000 に対し、モデル limit.context=81920 / output=8192 → 実発火は server ctx ~62–65K 付近（client 側 token 数が閾値超過時に client がトリガーするため server n_tokens とは厳密一致しない）。
  • case1 の 20260911_2 は 13h 超の長ランで、中断（cancel）タスクが多数。速度中央値は有効タスクのみで算出。
