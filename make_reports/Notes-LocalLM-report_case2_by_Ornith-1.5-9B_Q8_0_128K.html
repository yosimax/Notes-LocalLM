3-2. コンテキストサイズと処理速度の相関 (Context Size vs Speed)

case2 では ctx-size が 80K vs 128K と 1 変数に絞られる（両モデル 80K、Q4 128K）。残りの変数としてモデルサイズと量子化が作用するため、単なる「コンテキストサイズ」効果は分離しにくい。以下は整理した推論。

比較軸条件速度変化解釈
モデルサイズ9B → 27B~{apt4/aptw:.0f}× 減速パラメータ数 proportionally 影響。9B が 27B より圧倒的速い。
量子化Q4_K_M → Q8_0（9B内）生成 ~{agt4/agt8:.1f}→{agt8:.0f} t/s（~{agt4/agt8:.1f}× 減速）bit 数 up で処理データ量増＝減速。精度向上の代償。
コンテキストサイズ80K → 128K（9B内）速度差 negligibleQ4 は 128K を使用しつつ 80K の Q8 と同等速さ。→ 9B ではコンテキストサイズがボトルネックではない。
考察 / Observation — case2 から「9B クラスではコンテキストサイズ（80K vs 128K）が処理速度にはほぼ影響しない」ことが示唆される。速度の差は モデルサイズと量子化で支配される。27B はコンテキスト消費量が多いため、コンパクションの頻度が重要な因子になる（3-3 参照）。

4-1. コンテキストサイズ/時間経過と処理速度の逆相関 (Inverse Correlation)

プロンプト処理（＝累積コンテキストのデコード）の単一トークン時間（ms/token）をコンテキストサイズと相関付け。以下はピアソン相関。

相関 (Correlation)r解釈
入力トークン vs ms/token（c1_1）-0.548コンテキストが大きいほど ms/token が増大（逆相関）。
入力トークン vs ms/token（c1_2）-0.413同上、長時間セッションでも逆相関。
コンテキスト vs 生成速度-0.079生成速度はコンテキストに弱く依存（~4 t/s で安定）。
時間経過 vs 生成速度-0.191初期タスクの方がわずかに速く、時間経過で鈍る。

コンテキストが ~25〜38K に膨らんだタスクでは、ms/token が 26〜48ms に達する（対照的に小コンテキストは 0.05〜1ms/token）。

解釈 / Interpretation — コンテキストが大きいほど prompt 処理が非線形的に遅くなる。27B-Q2 は 80K の KV（Q8_0）が重いため、累積コンテキストが大きいほどデコード負荷が跳ね上がる。生成速度（~4 t/s）は比較的安定するが、プロンプト処理がボトルネックになる。

5. 補足・参考：Qwen3.8-27B-UD-Q2_K_XL パフォーマンス傾向 (Supplementary)

case1 の 2 セッションを比較。長時間リファクタリングでコンテキストが膨張し、逆相関（コンテキスト↑＝prompt処理↓）とコンパクション頻度の増加が顕在化する。生成速度は ~4〜4 t/s と安定。総プロンプト処理時間は両セッション合わせて ~4.0h に達する。

メモ / Note — case1 は yaml2epub.py の単一の大規模ファイルリファクタリング。OpenCode が計画→実装を反復し、各ラウンドが巨大プロンプト（既存コード全文）を含むため、prompt 処理がボトルネックになりやすいタスク構成。

6. 考察・まとめ (Observations & Summary)

  • 9B vs 27B：prompt 処理 ~3×、生成 ~2.7× 速い。24GB M4 では 9B-Q8_0 が「精度と速度」のバランスで使い物になる（case2 主モデル）。
  • Q4 vs Q8：Q8_0 は Q4 slower（生成 ~{agt4/agt8:.1f}×）だが精度向上。長時間・高精度タスクに有効。
  • コンテキストサイズ：9B では速度に影響せず、27B では消費量/コンパクション頻度に影響。
  • 逆相関：27B ではコンテキストが大きいほど prompt 処理が非線形的に遅れる（ms/token 26〜48ms）。
  • コンパクション：27B 長時限では ~21 件（実態発生間隔 ~16.5 分）、Q8 短タスクでは 7 件。Qwen3.8-27B 短タスクでは 0 件。
  • 24GB M4 安定動作：80K・Q8_0 KV をコンパクションで維持し、メモリスワップなしで長時間動作可能（case1 ~1165分）。
